# Паспорт проекта ИСР

## Назначение и стадия проекта

ИСР — Интерпретатор структур разделов. Он помогает испытателю подготовить раздел, просмотреть его структуру, выполнять директивы и взаимодействовать с программой проведения испытаний (ПРИС). Пользователи — испытатели космических аппаратов, в том числе операторы с небольшим опытом работы с ПК. Интерфейс должен ясно показывать состояние, доступные действия и ошибки. Конкретное поведение согласовывается с разработчиком и заказчиком.

Проект развивается одним разработчиком. Текущая версия перерабатывает ранее существовавшую Windows-реализацию на другом технологическом стеке. Цель первого релиза на Astra — сохранить полный набор возможностей ИСР для Windows. В новой версии можно исправлять проблемы и при необходимости добавлять возможности. Для уточнения ожидаемого поведения разработчик сверяется с документацией и с тем, как работает программа в Windows. Временные заглушки и незавершённые компоненты отражают стадию работы. Для регистрации дефекта требуется согласованное ожидание и свидетельство отклонения.

Разработчик принял результаты первичного онбординга. По его уточнению, первая поставка оператору состоится после выпуска полностью готовой релизной версии ИСР. Состав релиза и критерии готовности остаются открытыми. Текущие границы реализации описаны в ARCHITECTURE.md.

Источники назначения — документы D1 и D4 из перечня ниже, §§ 1.1 и 3.3 соответственно. Стадия проекта подтверждена разработчиком.

## Технологии и зависимости

- Язык — C++17. GUI и инфраструктура приложения — Qt 5.12.10. IDE разработчика — Qt Creator. Система сборки — qmake с генерацией Makefile.
- Основной проект — ISR.pro. Он объявляет Qt Core, GUI, Network и Widgets. Через JOBQT_SDK подключаются Logger и EncodingDetector версии 1.0.0. Наличие этих зависимостей проверяется отдельно в каждой среде. ISR.pro
- Указанный разработчиком qmake — /home/k0lup/Qt5.12.10/5.12.10/gcc_64/bin/qmake. В сеансе онбординга он сообщил qmake 3.1 и Qt 5.12.10. Путь относится к обследованной машине.
- Разработчик ранее указал GCC 6.3.0 (Debian 6.3.0-18+deb9u1). Фактический компилятор релизной сборки требует подтверждения. Поддержку отдельных возможностей C++17 следует проверять на утверждённом релизном инструментарии. Проект ограничен C++17 и API Qt 5.12.10.

## Среды и распространение

- Основная целевая среда — Astra Linux 1.7.5.16. Минимальная версия Astra и архитектура процессора требуют подтверждения. Целевое окружение предполагает работу без root и Интернета.
- Требуемая совместимость — glibc 2.24. Подтверждение относится к итоговому артефакту и целевой среде.
- Релизный процесс по информации разработчика — сборка и упаковка AppImage в контейнере Debian 9 с распространяемыми зависимостями. Образ, Dockerfile, скрипты, происхождение SDK и команды нужно подтвердить. Релизная упаковка выполняется только по отдельному согласованию.
- Windows и переносимость между Linux и Windows — направления развития. Версия Windows и фактическая поддержка подлежат проверке. Платформозависимые участки следует изолировать и обосновывать.
- В паспорте согласованные условия локальной компиляции относятся к Debian 12. Сеанс онбординга фактически проходил на Debian 13 с GCC 14.2.0 и GNU Make 4.4.1. Распространение разрешения на Debian 13 требует решения разработчика. Источник версии среды

## Локальная сборка и тестирование

- Согласованный объём локальной проверки на Debian 12 — безопасная компиляция в пределах правил проекта. До выполнения разработчик согласует среду, каталог артефактов, конфигурацию Debug/Release и команды сборки. Для отдельного сеанса с `team-build` область записи ограничена каталогом `build/codex-check/`.
- Перед компиляцией проверяются пользовательские шаги qmake, Makefile и скриптов. Локальная проверка ограничивается согласованными артефактами. Установка пакетов, make install, запуск приложения и обращения к внешним системам в неё не входят. ISR.pro задаёт путь установки в /opt для соответствующей Unix-конфигурации. Правила установки
- Найденный игнорируемый build/debug/Makefile свидетельствует о прежней генерации qmake с linux-g++, debug и qml_debug. Результат компиляции при онбординге не проверялся. Абсолютный RUNPATH локальных библиотек SDK в каталог Qt зафиксирован на обследованной машине. Для AppImage требуется отдельно проверить фактический состав и разрешение зависимостей.
- В основной сессии с `team-docs` команды компиляции передаются разработчику. Локальная компиляция, запуск тестов, проверка на целевой системе и релизная упаковка учитываются как отдельные проверки.
- Автотесты в текущей версии не заведены. Qt Test — кандидат. Решение об инфраструктуре, путях и способе изоляции внешних зависимостей принимает разработчик. Первый кандидат для обсуждения — ConfigParser::parseData на синтетических строках после согласования грамматики. ConfigParser
- В инженерной команде только QA пишет готовый код автоматических тестов, включая фикстуры и заглушки. В основной сессии QA передаёт его разработчику для ручного применения. QA может редактировать тесты напрямую только в отдельной согласованной среде с технически проверенным профилем `team-qa` и записью в утверждённые тестовые пути.
- До запуска изолированных тестов разработчик отдельно согласует среду, способ изоляции внешних зависимостей и команды запуска. В карточке задачи фиксируются согласованные и фактически выполненные команды, а также наблюдаемые результаты.

## Инженерный процесс и Git

- Основной код, архитектурные решения и приёмка принадлежат разработчику. Аналитик уточняет требования, тимлид проверяет предложенную декомпозицию, архитектор рецензирует дизайн, QA готовит тест-план, senior помогает с концепциями и отладкой, reviewer проверяет согласованный diff, mentor по запросу ведёт ретроспективу. Рабочий цикл
- В обсуждениях с разработчиком команда использует простые слова и описывает конкретные действия пользователя и ожидаемый результат. Профессиональные термины поясняются по мере необходимости.
- Координатор самостоятельно создаёт и редактирует Markdown в `.team/`. Он ведёт паспорт, архитектуру, требования, глоссарий, бэклог, карточки задач и журнал обучения, сохраняет результаты ревью и согласованные ADR. Подтверждённые факты, результаты проверок и согласованные решения можно сохранять без отдельного разрешения на каждую запись. После обновления координатор сообщает разработчику, какие файлы изменены и почему.
- Согласование с разработчиком требуется для изменения согласованных требований, принятия архитектурных решений, назначения приоритетов, закрытия задач, удаления документации и изменения оценок компетенций.
- На момент онбординга обследована ветка rewrite, HEAD 6a7da4fbe7ee291e6be41cde870763ec5abc135e. Локальная ссылка origin/rewrite указывала на тот же коммит. В репозитории видны также develop, master и reconstructions. Назначение веток и база ревью требуют подтверждения.
- Формальный стандарт оформления и правила ветвления не согласованы. Ориентир — стиль соседнего кода. Функциональные изменения и косметическое оформление следует разделять. В истории есть как узкие правки, так и коммиты с несколькими темами. Тимлид и senior объясняют индекс, атомарность коммитов, ветки и восстановление на примерах проекта.
- Агенты используют Git для чтения состояния, истории и diff. Операции записи, включая add, commit, push, fetch, pull, merge, rebase, reset, clean и switch/checkout, выполняет разработчик. Перед ревью согласуются база сравнения и охват неотслеживаемых файлов. Правила Git

### Как команда проверяет предложения разработчика

- Разработчик формулирует своё решение, объясняет, почему оно подходит, и называет наблюдение, которое могло бы изменить его мнение. Специалист начинает с одного конкретного вопроса о самом важном допущении. Если для ответа нужна незнакомая концепция, специалист сначала объясняет её простыми словами.
- Специалист сам сверяет доводы с доступным кодом, документацией или результатами проверок. Для значимого решения он ищет конкретный случай, где вариант может дать неправильный результат, и сравнивает его с рабочей альтернативой по целям и ограничениям задачи. Для небольшой правки достаточно проверки, соразмерной последствиям.
- Специалист поддерживает вариант, когда может объяснить, почему он предпочтительнее рассмотренных альтернатив. Он указывает, на чём основан вывод и какие ограничения у проверки. Если довод слабый или вариант хуже по важному критерию, специалист прямо объясняет, где проблема. Если данных мало, он называет одну проверку, которая поможет сделать вывод.
- Координатор передаёт этот порядок профильному специалисту при постановке задачи и сохраняет существенные возражения и результаты проверок в карточке. Если разработчик выбирает вариант при открытом возражении, в карточке отражаются его решение и причина выбора. Окончательное решение принимает разработчик.

## Использование ИИ и границы доступа

- Облачный ИИ используется в пределах разрешения работодателя, сообщённого разработчиком. Секреты и материалы вне разрешённого объёма обработке и передаче не подлежат. Передача в дополнительные сторонние сервисы требует разрешения.
- Агенты помогают объяснениями, подсказками, псевдокодом и посторонними учебными примерами. Агентам запрещено писать готовую реализацию основного кода или изменять его, включая патчи и рефакторинг, даже по прямому запросу. Запрет распространяется на сборочные конфигурации основного проекта. Размещать программный код в `.team/` для обхода ограничений запрещено.
- Агенты не используют sudo, не устанавливают зависимости, не меняют системные настройки и не выполняют разрушительные операции. ИСР, ПРИС, рабочие сервисы, оборудование и реальные испытательные сценарии не запускаются. Безопасная локальная компиляция ограничена условиями раздела о сборке.
- Личная карта компетенций — /home/k0lup/DeveloperProfile/SKILLS.md. Ментор использует её при ретроспективе и оценке по наблюдаемым результатам и предлагает обновления. Разработчик проверяет и сохраняет их вручную. В профиль не переносятся исходники и служебные сведения. Правила команды и профиля

### Профили разрешений команды

| Профиль | Назначение | Каталог записи | Техническая приёмка |
|---|---|---|---|
| `team-docs` | Профиль основной сессии для работы с инженерной документацией. Координатор ведёт Markdown по правилам команды. | `.team/` | Пройдена по сообщению разработчика. |
| `team-qa` | Отдельная согласованная сессия QA для редактирования автоматических тестов, фикстур и заглушек в утверждённых путях. | `tests/` | Требуется подтверждение перед использованием. |
| `team-build` | Отдельная сессия для согласованной локальной компиляции. | `build/codex-check/` | Требуется подтверждение перед использованием. |

Во всех трёх профилях сеть отключена, остальная часть рабочей области доступна для чтения. Перед использованием каждого нового профиля требуется технически проверить его в отдельной сессии и зафиксировать результат. Проверка подтверждает, что выбран нужный профиль, запись разрешена в предусмотренный каталог, запись за его пределами блокируется, а сеть недоступна. Согласование команд сборки и запуска изолированных тестов проводится отдельно от технической приёмки профилей. [Конфигурация Codex](../.codex/config.toml) · [Регламент команды](../AGENTS.md)
