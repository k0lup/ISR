# Паспорт проекта

## 1. Название и назначение

- Название: Интерпретатор структур разделов (ИСР).
- Назначение: совместная работа с программой проведения испытаний (ПРИС) с обменом данными по сети. ИСР обеспечивает взаимодействие пользователя с программой испытаний и интерпретацию директив.
- Пользователи: испытатели космических аппаратов, в том числе пользователи с небольшим опытом работы с ПК.
- Состояние: существующий проект, развиваемый одним разработчиком. Текущая версия ИСР представляет собой переработку ранее существовавшей Windows-версии, написанной на других технологиях.
- Цель переработки: сохранить согласованное назначение и необходимое поведение ИСР, улучшая реализацию, архитектуру и удобство работы там, где это обосновано. Побайтовое или построчное воспроизведение старой реализации не требуется.
- Желательное направление развития: кроссплатформенность Linux и Windows. В настоящее время основной целевой средой является Astra Linux; фактическая поддержка Windows и её минимальная версия пока не подтверждены.
- Требования к интерфейсу: простота и однозначность действий, понятное отображение текущего состояния, информативные сообщения об ошибках и предотвращение ошибочных действий пользователя. Конкретное поведение согласовывается с заказчиком.

## 2. Использование ИИ и границы данных

- По информации разработчика, использование облачного ИИ разрешено. Работать только в рамках фактически предоставленного разрешения работодателя.
- Не передавать пароли, токены, ключи и другие учётные данные, а также любую информацию, не разрешённую к передаче внешним сервисам. При сомнениях остановиться и запросить уточнение.
- Не отправлять данные в дополнительные сторонние сервисы без разрешения.
- Основной код пишет исключительно разработчик. Агенты анализируют требования, помогают проектировать решения, проводят ревью и обучают разработчика. Только QA вправе создавать готовый код автоматических тестов. Никто из агентов не создаёт готовую реализацию основного кода, даже по разовому запросу; допустимы объяснения, псевдокод и небольшие учебные примеры, не являющиеся решением текущей задачи. См. AGENTS.md.

## 3. Технологический стек

- Язык: C++17.
- Фреймворк: Qt 5.12.10.
- Компилятор, указанный разработчиком: `g++ (Debian 6.3.0-18+deb9u1) 6.3.0 20170516`. Уточнить фактические компиляторы и параметры для локальной и релизной сборок; не считать, что на Debian 12 используется та же версия.
- Учитывать ограничения GCC 6.3: заявленный стандарт C++17 не означает наличия всех возможностей языка и стандартной библиотеки C++17 в релизном инструментальном окружении. Проверять совместимость используемых конструкций и библиотек с фактическим компилятором.
- IDE разработчика: Qt Creator.
- Система сборки: qmake (Qt 5.12.10), с генерацией Makefile.
- Путь к qmake, указанный разработчиком: `/home/k0lup/Qt5.12.10/5.12.10/gcc_64/bin/qmake`. Проверить его доступность на машине Codex; не считать этот путь универсальным для контейнера или Windows.
- Не использовать возможности C++20 и более новых стандартов, а также API, отсутствующие в Qt 5.12.10.

- Среда повседневной разработки и работы Codex: Debian 12. Локальная сборка разрешена разработчиком в этой среде при соблюдении ограничений раздела 9 и AGENTS.md.

- Совместимость с glibc 2.24 и целевым окружением необходимо проверять на итоговом артефакте. AppImage сам по себе не гарантирует совместимость со старой системой.
- Не предполагать наличия дополнительных библиотек, сервисов или возможности установки пакетов на целевой машине.
- Новые зависимости и изменения способа сборки или распространения согласовывать с разработчиком.

## 5. Сборка и тестирование

### Локальная сборка (Debian 12)

- Codex разрешено выполнять безопасную локальную компиляцию на Debian 12. Сборка не означает разрешения на запуск приложения.
- Использовать qmake из Qt 5.12.10 по указанному в разделе 3 пути, если он доступен.
- Основной `.pro`-файл, конфигурация, рабочий каталог и полная команда сборки пока не указаны. Определить их по репозиторию и подтвердить с разработчиком перед первым запуском.
- Предпочитать отдельный каталог сборки вне исходников (shadow build), если это допускает проект. Создавать артефакты только в согласованном каталоге сборки. Не изменять исходники, `.pro`, `.pri` и другие проектные файлы для устранения ошибок сборки.
- Перед первым выполнением изучить пользовательские шаги qmake, Makefile и скрипты на предмет побочных действий. Не запускать команды, устанавливающие пакеты, обращающиеся к внешним системам или запускающие приложение.
- Успешная локальная сборка не доказывает совместимость итогового AppImage с glibc 2.24.
- Если песочница Codex работает в режиме read-only или AGENTS.md ограничивает выполнение проверок, не обходить ограничения: вернуть команды разработчику либо предложить отдельный согласованный сеанс сборки с записью только в каталог артефактов.

### Релизная сборка (Debian 9)

- Сборка и упаковка AppImage выполняются в контейнере Debian 9 для релизной версии.
- Не выполнять релизную упаковку автоматически при каждой задаче. Запускать только по отдельному согласованию.
- Dockerfile, образ, скрипты, фактический компилятор, путь к Qt и полные команды релизной сборки необходимо уточнить по имеющимся материалам.

### Тестирование

- Автоматических тестов в текущем проекте нет (подтверждено разработчиком). Каталог и тестовый фреймворк не определены.
- QA формирует тест-планы, критерии приёмки и предложения по автоматизированным тестам. Qt Test можно рассмотреть как кандидат, но решение о внедрении принимает разработчик.
- Только QA вправе писать готовый тестовый код, включая тестовые заглушки и фикстуры. В основной сессии он предоставляет его для ручного применения. Прямая запись допустима только в отдельной согласованной изолированной среде с технически ограниченным доступом к тестовым файлам. Каталог тестов и инфраструктуру предварительно согласовать. Изменения рабочего кода и его сборочных конфигураций выполняет разработчик.
- Проверки с внешними зависимостями выполнять только в согласованной изолированной среде; не обращаться к рабочим сервисам или реальному оборудованию.
- Различать предложенные, фактически выполненные и успешно пройденные проверки. Не считать компиляцию заменой тестированию.

## 6. Основные компоненты и точки входа

Предварительная карта по ранее обсуждавшейся архитектуре. Уточнить названия, пути, актуальность и ответственность компонентов по текущим исходникам; этот раздел не является подтверждённым описанием реализации.

- Точка входа: определить по исходникам (обычно main.cpp).
- GUI: отображение программы испытаний, состояния выполнения и взаимодействие с пользователем.
- Интерпретатор директив: разбор и исполнение директив; базовый класс Direct и специализированные классы директив.
- Исполнитель директив: управление последовательностью выполнения и состоянием исполнения.
- Controller / RequestManager: управление взаимодействием компонентов и асинхронными запросами; актуальную реализацию проверить.
- Сетевой обмен с ПРИС: обработка входящих и исходящих сообщений; транспорт и протокол уточнить по реализации и документации.
- Вспомогательные сервисы: конфигурация, журналирование, загрузка разделов и обработка кодировок; состав уточнить по репозиторию.

Детальную архитектуру, потоки, зависимости, жизненные циклы объектов и принятые архитектурные решения вести в .team/ARCHITECTURE.md.

- Не допускать неявного изменения семантики директив, форматов сообщений и согласованных сценариев работы.

- Предлагать решения соразмерно задаче; избегать усложнения архитектуры без обоснованной необходимости.
- Любые новые требования, предположения о предметной области и критерии приёмки подтверждает разработчик совместно с заказчиком при необходимости.

## 8. Стиль кода и контроль версий

- Формального стандарта оформления нет; ориентироваться на существующий стиль проекта и окружающий код. При неоднозначности предложить варианты, а не навязывать новый стандарт.
- Не проводить массовое форматирование и переименование вне рамок текущей задачи.
- Отдавать предпочтение читаемому коду, явной ответственности компонентов и понятным именам.
- Разделять функциональные изменения и косметический рефакторинг.
- Git используется. Формализованные соглашения о ветках, коммитах, тегах и интеграции изменений пока отсутствуют.
- Агенты могут выполнять безопасные операции чтения Git: `git status`, `git diff`, `git diff --cached`, `git log`, `git show`, `git branch --list`. Перед ревью уточнять базу сравнения и учитывать неотслеживаемые файлы отдельно.
- Тимлид и Senior помогают разработчику освоить Git на реальных задачах: объясняют модель working tree / index / commit, атомарные коммиты, ветки, разрешение конфликтов, восстановление изменений и выбор подходящего процесса работы. Ментор отслеживает прогресс.
- Предлагать команды Git с пояснением их эффекта и рисков; операции, изменяющие состояние репозитория, выполняет сам разработчик. Не выполнять add, commit, push, pull, fetch, merge, rebase, reset, clean, switch/checkout и другие изменяющие операции за него.
- Не создавать удалённые репозитории и не публиковать исходники. Не вводить обязательный Git Flow, Conventional Commits или иные соглашения без обсуждения.

## 9. Ограничения на действия агентов

- Не писать и не изменять основной код, в том числе не выдавать готовые патчи или готовые функции для текущей задачи. Документацию и конфигурации предлагать текстом для ручного применения. Только QA может создавать тестовый код; прямые записи тестов допустимы лишь в отдельной технически ограниченной среде (см. раздел 5).
- Не устанавливать пакеты, не использовать sudo, не менять системные настройки.
- Не запускать ИСР, ПРИС, испытательные сценарии или сетевой обмен с реальным оборудованием и рабочими сервисами.
- Не выполнять сборку или тестирование на реальном оборудовании. Локальная компиляция на Debian 12 разрешена в пределах раздела 5; фактические команды и каталог сборки должны быть согласованы. Запуск приложения, релизная упаковка и запуск новых тестов не входят в это разрешение.
- Не изменять форматы директив, сетевые протоколы, внешние интерфейсы и требования без согласования.
- Не удалять файлы и не выполнять разрушительные операции.
- Не принимать окончательные архитектурные решения и не закрывать задачи от имени разработчика.
